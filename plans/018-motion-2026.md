## Why this matters

The dashboard already receives a staggered entrance (`.dash-grid4 > *`) but
navigating to Lançamentos or Horizonte shows a plain fade with no per-item
rhythm — the screens feel static compared to the dashboard. At the same time,
two hardcoded millisecond values (`0.9s` in App.css and `480` in ThemeToggle.tsx)
bypass the design-system motion tokens, so a future token change would not
cascade to them. A one-frame opacity flash on `.ak-screen` also bleeds through
because `animation-fill-mode: backwards` is missing on the screen-enter rule.
This plan wires every animation to the DS tokens, adds `backwards` to screen-enter,
and brings a tasteful staggered entrance to the two static list screens — all
gated behind `(prefers-reduced-motion: reduce)` which collapses token durations
to 0 ms (the existing mechanism already in `tokens/motion.css`).

### Motion tokens (motion.css lines 7–12 and 28–35)

```css
/* src/design-system/tokens/motion.css lines 7–18 */
:root {
  --dur-instant: 80ms;
  --dur-fast: 130ms;
  --dur-base: 200ms;
  --dur-slow: 320ms;
  --dur-deliberate: 480ms;

  --ease-standard: cubic-bezier(0.2, 0, 0, 1);
  --ease-entrance: cubic-bezier(0.16, 1, 0.3, 1);
  --ease-exit: cubic-bezier(0.4, 0, 1, 1);
  --ease-calm: cubic-bezier(0.33, 0, 0.2, 1);
}

@media (prefers-reduced-motion: reduce) {
  :root {
    --dur-instant: 0ms;
    --dur-fast: 0ms;
    --dur-base: 0ms;
    --dur-slow: 0ms;
    --dur-deliberate: 0ms;
  }
}
```

The token `--dur-deliberate` = 480 ms; `--dur-slow` = 320 ms.
There is currently **no** `--dur-stagger-step` token for list-row delays.

### Step 7: Fix ThemeToggle — read `--dur-deliberate` from CSS at runtime

Open `src/shell/ThemeToggle.tsx`. The `playReveal` function currently uses a
hardcoded `duration: 480` (line 53). Replace it with a helper that reads the

Replace the `playReveal` function body — specifically the `overlay.animate(...)`

```tsx
// Read the token at call time so future DS changes propagate automatically.
const durMs =
  parseFloat(
    getComputedStyle(document.documentElement).getPropertyValue("--dur-deliberate"),
  ) || 480;

const anim = overlay.animate(
  [
    { clipPath: `circle(0px at ${x}px ${y}px)`, opacity: 0.9 },
    { clipPath: `circle(${radius}px at ${x}px ${y}px)`, opacity: 0 },
  ],
  {
    duration: durMs,
    easing: "cubic-bezier(0.16, 1, 0.3, 1)", // --ease-entrance
  },
);
```

`getPropertyValue` returns a string like `" 480ms"` or `" 0ms"`.
`parseFloat` strips the unit (ms) and leading whitespace, returning the numeric
milliseconds value. The `|| 480` fallback handles the WAAPI-less / jsdom path
where `getComputedStyle` may return an empty string.

The `prefersReducedMotion()` guard on line 75 already short-circuits before
`playReveal` is called in the reduced-motion case, so the 0 ms collapse from
the token is a belt-and-suspenders backstop only.

## Maintenance notes

- **Token ceiling**: the `--dur-deliberate` token (480 ms) is the longest
  intentional duration. If future work extends this ceiling, the ThemeToggle
  will pick it up automatically (after this plan lands); no additional change
  needed there.
- **Stagger cap**: The 12-row explicit cap for `.txn-table tbody tr:nth-child(n)`
  means rows beyond 12 all animate with the same max delay (~440 ms). For lists
  of 500+ rows this is fine — the last visible rows on screen all animate
  together after a short pause, which reads as "the rest loaded". If pagination
  is ever added, the stagger resets naturally on each page render.
- **Horizonte column count**: The 6-column cap matches the typical 6-month
  forecast horizon. If the forecast is ever extended beyond 6 months, add more
  `:nth-child` rules to `nk-horizon-cols > div`.
- **PR reviewer checklist**: confirm (1) no money cells have `animation` applied,
  (2) the `@media (prefers-reduced-motion: no-preference)` wrappers are present
  on both new stagger blocks, (3) `--dur-stagger-step: 0ms` is in the
  reduced-motion `:root` override in `tokens/motion.css`.
- **Follow-up deferred**: The `.nk-pop--bottom` / `.nk-pop--top` tooltip
  animations at App.css lines 810–815 also use hardcoded `0.16s`; they were left
  out of this plan because they are close to `--dur-fast` (130 ms) but not exact,
  and changing them risks tooltip timing. A separate clean-up plan can address
  that value when a `--dur-micro` token is introduced.
